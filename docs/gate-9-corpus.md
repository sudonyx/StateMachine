# Gate 9 adversarial corpus

## Fixed source and seed

The checked-in `test-data/orion-gate9-deliveries.ndjson` is generated by `tools/OrionGate9Corpus`. The default seed is `20261019`; its deterministic `System.Random` usage and stable JSON property order produce byte-identical UTF-8 NDJSON for the same seed and Orion definition.

Regenerate and independently validate from the repository root:

```powershell
dotnet run --project tools\OrionGate9Corpus -- generate --seed 20261019
dotnet run --no-build --project tools\OrionGate9Corpus -- validate --seed 20261019
```

Validation checks the actual Orion 4.0 definition and reports failures rather than silently accepting unsupported records. It counts additional deliveries beyond the first occurrence: `sum(group size - 1)` for exact event-ID duplicates, and distinct logical event IDs beyond the first for semantic duplicates. Exact duplicate groups must have identical immutable message content; delivery ID and delivery time may differ.

## Definition and vocabulary

The input vocabulary is derived from `definitions/orion-v4.json`. Corpus `event_type` values are mapped workflow events:

`AcceptOffer`, `Approve`, `Cancel`, `CustomerNotified`, `DeclineOffer`, `DocumentsReceived`, `EquipmentReserved`, `IssueOffer`, `ReferForReview`, `Reject`, `Submit`.

The corresponding command/observation `input_type` values are:

`AcceptOffer`, `ApproveAssessment`, `CancelApplication`, `CustomerNotified`, `DeclineOffer`, `DocumentPackageReceived`, `EquipmentReserved`, `IssueOffer`, `ReceiveDocuments`, `ReferForReview`, `RejectApplication`, `SubmitApplication`.

`event_id` is the logical event/message identity passed as API `messageId`; `delivery_id` is retained separately in each receipt. Command `operation_id` and observation `observation_id` are also distinct. Observation `correlation_id` is the registered expected-operation identity. The runner establishes expected operations at the matching current revision with the trusted setup endpoint before the relevant observation, including late observations that must be correlated before cancellation.

Each application carries deterministic initial facts in `instance_facts`. The 300 IDs are grouped into document-wait/cancellation, offer-decline/competition, and offer-acceptance/reservation/notification lifecycles. The harness-free reservation and notification observations use the existing declared Orion mappings, trusted source names and required evidence. No transition targets or expected results are included.

## Independently validated counts

The seed-20261019 report is:

| Measure | Count |
|---|---:|
| Deliveries | 5,000 |
| Distinct application IDs | 300 |
| Additional exact duplicate deliveries | 150 |
| Additional semantic duplicate requests with different event IDs | 100 |
| Late deliveries, using a prior-later-occurrence versus delivered-time comparison | 450 |
| Race pairs | 75 |
| Missing-required-evidence malformed payloads | 50 (1.00%) |
| Pre-cancellation document results delivered after cancellation | 100 |

Categories overlap: the 150 exact duplicates include 25 duplicated `EquipmentReserved` observations; duplicates can also qualify as late. A race pair is one declared two-delivery `race_group` on the same application and expected revision, with delivery timestamps no more than 100 ms apart. Malformed payloads are observations missing one or more `requiredEvidence` names from the immutable definition, not expected-outcome flags.

The event list is derived from used records and is a subset of the supported Orion event vocabulary. The validator checks required fields, UTC-offset ISO timestamps, unique delivery IDs, input/event vocabulary, per-group duplicate payload consistency, race shape/window/revision, late-event counts, cancellation ordering, malformed percentage and byte-for-byte regeneration.

## Corpus runner

The runner initializes 300 uniquely prefixed runtime instances and submits all 5,000 deliveries through `/commands` or trusted `/observations`; it does not use `/events`. It processes each application in delivery-time order, runs declared race pairs concurrently in `concurrent` and `multi-host` modes, and bounds the number of active application lanes. `delivered_at` controls fixture dispatch order only; `occurred_at` is sent as a claim and cannot override the API clock.

Start the API with an isolated SQLite path and configured trusted ingestion key, then run:

```powershell
$env:DURABLE_STATE_MACHINE_DB = ".\gate9-run.db"
$env:DURABLE_STATE_MACHINE_TRUSTED_INGESTION_KEY = "<local-test-key>"
$env:ASPNETCORE_URLS = "http://localhost:5000"
dotnet run --project src\DurableStateMachine.Api

dotnet run --project tools\OrionGate9Corpus -- run `
  --base-url http://localhost:5000 `
  --trusted-key "<local-test-key>" `
  --mode concurrent `
  --concurrency 8 `
  --run-id gate9-run-1
```

Modes:

- `baseline`: one lane, serial delivery within each application, including race pairs.
- `concurrent`: bounded independent application lanes and concurrent declared race pairs on one API host.
- `multi-host`: same as concurrent but round-robins across two or more `--host-url` values. All hosts must point at the same SQLite file; the runner does not configure or validate that deployment detail.

Use a fresh database and a unique `--run-id` for repeat runs. Reports default to the system temporary directory or can be written with `--report`. A zero exit code means the completed run passed the declared history, revision, duplicate acceptance, timer uniqueness and effect-operation uniqueness checks; HTTP/setup failures and invariant failures are reported and produce a non-zero exit.

The runner does not process overdue timers or invoke the Generic Harness. Timer deadline processing and provider correlation remain covered by the Gate 7/8 integration tests; timer rows and generated effect intents are inspected for duplicate identities after the corpus run.
