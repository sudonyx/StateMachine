# Gate 10 crash and recovery matrix

The test-only interruption controls are mapped only in Development when `DURABLE_STATE_MACHINE_ENABLE_TEST_CONTROLS=true`. Exception injection is not equivalent to operating-system process termination. “Host-restart verified” refers to disposing and recreating the API test host against the same SQLite file, in one test process. Child-process tests terminate only their owned API process at the boundaries shown below, then start a fresh process against the same disposable SQLite file.

| # | Interruption point | Durable boundary and expected recovery | Verification status |
|---|---|---|---|
| 1 | Before intake commit | The request is not recoverable until the first SQLite transaction commits. | **Deterministic fault-injection verified**: no inbound receipt remains. |
| 2 | After intake commit, before evaluation | Canonical envelope, digest, identity, original revision, definition binding and authority classification remain in `InboundMessages` as `Received`. A receipt-specific resume reuses that data. | **Operating-system process-kill verified** and **deterministic fault-injection verified**: a new process resumes once with one accepted history row. |
| 3 | During guard evaluation | The guard is pure. Its transaction rolls back, leaving intake `Received`; continuation re-evaluates using stored facts/evidence and no external decision fetch. | **Deterministic fault-injection verified**; recovery after this exact interruption is tested in the same restarted test host. No new Meridian request is made by the recovery path. |
| 4 | External work pending | Effect intent and expected operation remain durable before provider dispatch. Recovery reads local status without submitting a replacement. | **Operating-system process-kill verified** at the committed-intent/before-provider boundary: a fresh process reports pending external work and the provider was not called. |
| 5 | Verified external result before local acceptance | The trusted Generic Harness adapter validates the response and correlation, then commits the immutable result payload, evidence, identities, operation/definition binding, execution revision and digest to `StagedObservations` before Gate 5 evaluation. A result staged before cancellation remains evidence but cannot reactivate a terminal instance. | **Operating-system process-kill verified after the staging commit**: a fresh process resumes the stored result without another Harness execution and creates one accepted transition. **Deterministic fault-injection verified** before/during staging, before evaluation, during finalization and after commit. A crash after remote completion but before this local staging commit remains an unresolved response-loss window. |
| 6 | During final transition/projection persistence | The receipt final status, attempt/evidence, accepted state/revision/history, timers, effects and expected-operation resolution commit in one SQLite immediate transaction. A child API killed at the pre-final-save pause restarts with the prior projection and `Received` intake. | **Operating-system process-kill verified** immediately before final persistence; **deterministic fault-injection verified** at finalization/projection-save boundaries; existing SQLite trigger tests exercise a write failure. No kill during an individual SQL statement. |

## Cross-cutting verification and limitations

- Replay/recovery integration tests inject a counting HTTP handler for the Generic Harness and assert zero calls while running reconstruction, decision verification and repeated recovery assessment. They compare instance, attempts, receipts, expected operations, timers, effects and transition history before and after.
- Existing SQLite immediate transactions, conditional revision updates and unique accepted-history revision constraints remain the cross-host arbitration mechanism. Two independent API hosts sharing SQLite exercise staged-result continuation against a competing command, cancellation and timer expiry, checking both relevant commit orders.
- Process termination is verified after intake commit/before evaluation, after effect-intent commit/before provider dispatch, immediately before final local persistence, and after verified-result staging commits. It is not verified during an individual SQL statement or before the staging transaction commits.
- The staged response body is durable after the trusted adapter's staging commit. A remote result that completed but was not yet staged before process loss remains unavailable; unknown outcomes are not inferred from Harness status, and no external side effect is automatically replayed.
- No historical intake is synthesized for pre-Gate-10 records. Older attempts lacking Gate 4 evidence remain state-reconstructable but not decision-verifiable.
